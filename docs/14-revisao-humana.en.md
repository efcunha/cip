## 📋 Human Evaluation Rubric

Each architect evaluates 20 scenarios using **exactly the same rubric** as the automated scoring (1-5 per criterion):

| Criterion | Definition | 1 (Terrible) | 5 (Excellent) |
|---|---|---|---|
| **Accuracy** | Technical correctness of the content | Wrong or invented facts | 100% correct, no hallucination |
| **Grounding** | Answer anchored to an official source | No source, "guesswork" | Cited official URL + framework |
| **Citation** | Citations in the `[cloud, service, title, url]` format | No citations | ≥3 well-formed citations |
| **Format** | Answer structure | Running text, no order | Summary + findings + plan + references |
| **Zero-Price** | No prices inferred from memory | Cited specific $ without a live tool | No price (or only from a tool) |

### Behavioral Scale

```
1 — Terrible:   Unusable answer, severe errors or hallucinations
2 — Poor:       Answer fails the basics, requires complete rewrite
3 — OK:         Usable answer but with significant gaps
4 — Good:       Solid answer, small adjustments needed
5 — Excellent:  Exemplary answer, can go straight to production
```

## 📊 Review Workflow

### Step 1: Automated Scoring
```bash
python eval/run_eval.py --api http://api.cip.internal --report-md --strict
```
- Runs 95 cases (60 knowledge + 10 IAC + 5 compare + 10 sec + 10 cost)
- Calculates automated scores
- **Gate**: blocks if any criterion < 4.0 OR > 5% zero-price violations

### Step 2: Scenario Assignment
Each architect receives 20 balanced cases:
- 7-8 **knowledge** cases (cloud-aligned with their specialty)
- 4-5 **IAC review** cases
- 3 **multi-cloud comparison** cases
- 2-3 **cost** cases
- 2 **security** cases

**Distribution**: 5 architects × 20 cases = 100 human reviews (each case evaluated by 1 specialist architect + weighted average).

### Step 3: Manual Evaluation
For each case, the architect:
1. Reads the question + payload (if any)
2. Analyzes the answer generated by the LLM
3. Marks 1-5 scores for each criterion
4. Adds qualitative observations (optional)
5. Submits via form (Google Forms / Notion / GitHub PR)

### Step 4: Consolidation
```python
# Consolidation pseudo-code
for case in cases:
    auto_score = auto_eval[case.id]
    human_scores = [r.score for r in human_reviews[case.id]]
    
    # Weighted average: 60% human, 40% automatic
    final_score = weighted_mean(human_scores, weight=0.6) + \
                  weighted_mean(auto_score, weight=0.4)
    
    # Flag for additional review if divergence > 1.0
    if abs(human_avg - auto_score.avg) > 1.0:
        flag_for_extra_review(case.id)
```

### Step 5: Final Gate
| Criterion | Final score | Status |
|---|---|---|
| Accuracy ≥ 4.0 (all cases) | Computed | Go/No-Go |
| Grounding ≥ 4.0 | Computed | Go/No-Go |
| Citation ≥ 4.0 | Computed | Go/No-Go |
| Format ≥ 4.0 | Computed | Go/No-Go |
| Zero-Price ≥ 4.0 | Computed | Go/No-Go |
| Median cost < $0.05 | Computed | Go/No-Go |
| No case with accuracy < 3.0 | Computed | Go/No-Go |

**Block**: any criterion fails → **NO-GO** until the regression is resolved.

## 📈 Acceptance Criteria by Category

### Knowledge (60 cases)
- ≥90% of answers must cite an official source (clickable URL)
- Accuracy ≥ 4.5 (factual knowledge is easier to validate)
- Trade-offs must be explicit when relevant
- **Trade-off**: multi-cloud comparison must use a table

### IAC Review (10 cases)
- ≥80% of findings must have correct severity
- At least 1 critical finding for payloads with severe problems
- Recommendations must be actionable (not generic)
- $ impact estimate when relevant (FinOps)

### Comparison (5 cases)
- Table mandatory when comparing 3+ options
- Trade-offs must cover: cost, complexity, resilience, vendor lock-in
- Each cloud must have ≥2 specific features mentioned

### Cost (10 cases)
- ≥80% of answers must guide collection via a live tool
- When tools are unavailable: declare explicitly and suggest how to collect
- $ range estimates are acceptable (not exact price)

### Security (10 cases)
- Recommendations must cite a framework (WAF, CIS Benchmarks, etc.)
- Severity must follow CVSS / OWASP standard when applicable
- The trade-off between security and usability must be mentioned

## 🔄 Iteration Process

When the gate fails:

1. **Root cause analysis**: failure pattern (always the same criterion? same cloud?)
2. **Targeted fix**:
   - Accuracy < 4.0 → review ingestion + add official source
   - Grounding < 4.0 → adjust retrieval_min_score or expand the base
   - Citation < 4.0 → reinforce the system prompt
   - Format < 4.0 → review the response template
   - Zero-Price violations → block tools-only on pricing questions
3. **Re-run eval**: the gate must pass to promote
